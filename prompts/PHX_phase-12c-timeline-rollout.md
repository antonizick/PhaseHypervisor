## Tasks
1. **Inventory and idle check.** For each of the four repos, record:
   - is it idle: no `🔄` row on `main`, no `phase-*` worktree, `main` clean, no running `phx` lock under `$XDG_RUNTIME_DIR/phx/`;
   - does it have a remote, and a final report;
   - what `phx plan <repo>` prints (save the output).

   **Skip any repo that is not idle** and record it as a follow-up with the reason. Never commit another agent's files.
2. **Apply the recipe** from the skill's "Adding the visual timeline to an existing repo" to each idle repo, exactly as written. If a step does not fit a repo, stop and fix the recipe in the skill (in this repo, on the phase branch) rather than improvising per repo:
   - copy `scripts/phase_timeline.py` byte-identical from the skill;
   - add the markers to the plan after the phase table, and to the final report if one exists;
   - add the maintenance lines to the repo's shared instructions, `.claude/commands/phase.md` and `phase-add.md`, keeping the repo's own text;
   - run `python3 scripts/phase_timeline.py --write --vault-note "<vault note>"`.
3. **Look at each result.** Render each repo's SVG to PNG in the scratchpad, Read it, and compare it with that repo's Phase Log: every phase that has times is shown, approximate ones are marked, and no phase appears that does not exist. If a repo's data exposes a generator bug, fix it in the skill copy (with a test in `tests/test_phase_timeline.py`), re-copy the script and regenerate. Keep PHX's own copy identical.
4. **Commit per repo.** One commit, `chore(docs): add visual timeline`, staging explicit paths only. Add an ADR in that repo's decisions log (with its index row) and a timestamped line in its vault note. Push if the repo has a remote. If a repo has a rule stricter than ADR-0004, follow it and flag it.
5. **Verify.** For every repo: `phx plan <repo>` is byte-identical to task 1's output, `--check` passes, and `git status` is clean. Run `/phase status` logic (read-only) and confirm it reports no drift.
6. **Close the loop in PHX.** Add a short "Retrofit results" note to the skill's migration section, listing each repo and what was odd about its data (one line each, no private content). The section is public, so the deny-list applies: name no repos there; the per-repo details go in this phase's Phase Log.
