# PHX Phase 12a: Shareable method package (plugin, generic skill, getting-started guide)

**Model:** Opus 5.5 (`/model claude-opus-5-5`) · **Depends on:** 12 · **Branch:** `phase-12a-shareable-method-package` · **Worktree:** `../PhaseHypervisor-phase-12a` · **Gate:** review

PHX v0.1.0 is released and the repo is public, but nobody except Nick can use it as intended. The `phx` program is close to portable. What a new user also needs is the `phased-project` skill (which writes each repo's `/phase` and `/phase-add` commands), the `/phx` command and the standing rules those assume. Today all of that lives only in Nick's `~/.claude`, full of his paths, his name, his vault and his private repos. This phase makes the PHX repo the **single source** of the method's skill and commands. It ships them as a Claude Code plugin (with a manual-copy fallback) and adds a public guide explaining how every piece fits together. Nick then switches his own install to the packaged copy, so he uses exactly what others get.

## Read first
`CLAUDE.md`, `prompts/PHX_shared-instructions.md`, ADR-0004, ADR-0011, ADR-0012, ADR-0018 and **ADR-0022** (this phase's decisions), `docs/PHX_AUTO_MODE_CONTRACT.md`, `docs/PHX_USER_GUIDE.md`, `SECURITY.md`, the Phase Log entries for 03, 09 and 12, and the planning entry for 12a. Outside the repo, read in full: `~/.claude/skills/phased-project/SKILL.md` and every file in its `templates/`, `~/.claude/commands/phx.md`, Nick's global `~/.claude/CLAUDE.md`, and the playbook `/home/nick/Documents/04 Resources/Claude Code Phased Project Method.md`. Check the current Claude Code plugin and marketplace format (use the `claude-code-guide` agent or the docs, and `claude plugin --help` on the installed 2.1.310). ## Nick's request (verbatim intent, 2026-10-27 05:14 CDT)
> Is it possible? Is it practical? to add to the PHX Repository the dependencies and instructions a user would need to take advantage of the whole /phased-project and /phase system we have built. In short, is it possible to package up and share in a manner that would allow a user to deploy the Claude skills and commands that a User would need so that they too could use the PHX system? We would need to add to the [PHX] repository not only the skills and commands but also basic instructions on how all of these tools and commands work together

Planning answered "possible and practical". Nick then chose (2026-10-27 05:14 CDT): **(1)** the repo is the source of truth, **(2)** plugin plus a manual-install fallback, **(3)** a new public guide written for strangers, with the private playbook kept as Nick's own note.

## Decisions already made
- **ADR-0022**: the repo is the source of truth. Ship as a Claude Code plugin from a marketplace in this repo, plus a manual-copy fallback. Write a new public guide, and keep Nick's playbook private, linking to the guide.
- ADR-0011: manual `/phased-project` and `/phase` stay fully supported, and PHX stays opt-in. The package must work for someone who never installs `phx`.
- ADR-0004: committing, merging and pushing `main` is fine. **The repo is public (since 2026-10-27 04:59 CDT), so every push publishes.** Pushing a version tag, running `claude plugin tag`, or creating a GitHub Release needs Nick's confirmation; ask in the close-out message.
- ADR-0012: the contract stays version 1. Generalising wording must not change the `PHX-CONTRACT: 1` marker, step 0, the `PHX-CHECK-DONE` sentinel (ADR-0020) or the `PHX-RESULT` grammar.

## Goal
A stranger with Linux (macOS best-effort), Claude Code and `uv` can follow one README section to: install the plugin; bootstrap a phased project with `/phased-project`; run phases by hand with `/phase` and add work with `/phase-add`; and optionally install `phx` to run phases hands-off and drive it with `/phx`. Nick's own setup runs from the same files and behaves as it does today.

## Tasks
1. **Plugin layout.** Create the plugin in the repo, in the layout the current docs require. Default: `.claude-plugin/marketplace.json` at the repo root (marketplace `phasehypervisor`, owner `antonizick`), listing one plugin `phased-project` at `plugins/phased-project/`, which holds `.claude-plugin/plugin.json` (version `0.1.0`, MIT, homepage the repo), `skills/phased-project/` (SKILL.md and `templates/`) and `commands/phx.md`. Find out how plugin skills and commands are namespaced (for example `/phased-project:phased-project`). Make sure `/phased-project` and `/phx` work as typed, or document the exact names users must type. Decide, in an ADR, how a user's existing un-namespaced copy is handled. `claude plugin validate` must pass on the marketplace and the plugin.
2. **Generic skill (the repo copy becomes the source).** Copy Nick's live skill and templates into the plugin, then generalise them:
   - "Nick" becomes "the owner" (or `{{OWNER}}` where a template writes it into a project). The commands' wording to the human stays the same in meaning.
   - Fixed paths become settings read from an optional **"Phased-project settings"** section in the user's global `~/.claude/CLAUDE.md`: owner name, work root, vault root and projects folder, playbook or guide note, OS-modifications log, reference implementation. Every setting is optional. With no vault, the vault note and vault log steps are skipped and reported. With no OS log, that close-out item reads "if the project keeps one". With no reference implementation, the agent uses this repo's own plan and prompts as the worked example.
   - Remove history that only makes sense for Nick ("MeetingMaster3 ADR-0030", "migrated on 2026-10-26 by PhaseHypervisor Phase 09"). Where a rule depends on that history, keep the rule and give the reason in one line.
   - Keep the method's substance, its exact conventions and the hands-off contract text byte-for-byte where it matters (task 8 checks this).
3. **Generic `/phx` command.** `commands/phx.md`: no absolute paths, no project aliases baked in. The repo argument is a path, or a name under the work root from the settings section, if one is set. The guide is linked by its GitHub URL. If `phx` is not on PATH, the command says how to install it (`uv tool install git+https://github.com/antonizick/PhaseHypervisor`) and stops. Keep every safety rule of the current command: always `--detach`, confirm before `run`/`resume`, never answer questions or stop runs unasked, never read key files.
4. **Standing rules for new users.** Add `examples/CLAUDE.user.md`: a block to paste into `~/.claude/CLAUDE.md` containing the "Phased-project settings" section (commented placeholders) and the standing rules the method relies on, in generic form. These are: timestamps from `date`, the project prefix rule, the git authority rule with its public/release/force-push exceptions, and an optional model fit check. Say plainly which parts are optional and what each one changes.
5. **Public guide.** Write `docs/PHX_GETTING_STARTED.md` for strangers. Cover: what the pieces are (the method, `/phased-project`, per-repo `/phase` and `/phase-add`, the plan and prompts it creates, `phx` and `/phx`) with one diagram of how they connect. Then prerequisites; install (plugin, then manual copy into `~/.claude/skills` and `~/.claude/commands`, then optional `phx` via `uv tool install`); a first-project walkthrough (bootstrap → `/phase status` → `/phase` → `/phase-add` → optional `phx preflight` and `phx run --detach`); the safety model (bypassed permissions only in hands-off runs, risk rule, Gates, what needs human confirmation); updating and uninstalling; troubleshooting; and what is optional (`ai-provider`, vault, notifications, `--detach` on non-systemd hosts). Nothing private copied from the playbook. Link it from the README ("Use PHX yourself" section near the top) and from the user guide.
6. **Switch Nick's install to the repo copy.** Back up `~/.claude/skills/phased-project` and `~/.claude/commands/phx.md` (timestamped, as earlier phases did). Add Nick's real values to a "Phased-project settings" section in his global `~/.claude/CLAUDE.md`, keeping his existing rules. Then make his install use the repo files. Default: replace the skill directory and `phx.md` with symlinks into the main checkout, so edits land in the repo and the names stay un-namespaced. Use the plugin install instead if the docs show that is cleaner, and record the choice in the ADR. Without starting a Claude session (no tokens), confirm the skill and command still resolve, by listing them or reading the resolved files. **Risk rule:** this changes the live setup that every future project depends on. If the regression check in task 8 shows any behavioural difference you cannot explain, stop and ask Nick (hands-off: block-with-question) rather than switching.
7. **Docs and portability wording.** README "Requirements": `ai-provider` becomes optional (with the fallback explained), and Linux is stated as supported, macOS as untested (no `--detach`, no notifications). Update `docs/PHX_USER_GUIDE.md` the same way, plus a pointer to the getting-started guide. Update `SECURITY.md` with a section on what installing the plugin lets agents do and the bypassed-permissions caveat. Update threat model T19 (the `ai-provider` on another user's PATH is that user's trust decision). Update `docs/PHX_ARCHITECTURE.md` (the plugin as a component), `CLAUDE.md` rule 7 (skill changes are now made in `plugins/phased-project/`, and mirrored in the public guide and Nick's playbook), and the repo's `CONTRIBUTING.md` (how to change the skill and check it). Update the playbook note itself: its "where the skill lives" text points at the repo, and it links the public guide.
8. **Regression check (ADR-0011 for the generalisation).** Render every template with dummy values, once with a full settings section and once with none. With Nick's settings, the rendered `phase-command.md`, `phase-add-command.md` and `_shared-instructions.md` must differ from his pre-phase live copies (the backup) only in owner and path wording. In particular `PHX-CONTRACT: 1`, step 0, `PHX-CHECK-DONE`, the hands-off section and the `PHX-RESULT` lines must be identical. Record the diff summary in the Phase Log. `phx plan` on this repo and on `/home/nick/Work/MeetingMaster3` (read-only) must report the same as before.
