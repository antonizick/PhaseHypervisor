# PHX Phase 12d: Run progress heartbeat, live `phx status` and `phx watch`

**Model:** Opus 5.5 (`/model claude-opus-5-5`) · **Depends on:** 12c · **Branch:** `phase-12d-progress-heartbeat` · **Worktree:** `../PhaseHypervisor-phase-12d` · **Gate:** review

Phases 00–12c built a supervisor that runs for hours or days, but it is dark while it works. During one phase session (typically 20–60 minutes) `run.jsonl` gets nothing at all: the only movement is `state.json`'s `last_event` timestamp, rewritten at most every 30 s and saying only that *something* arrived. Nick launches long runs and has no way to tell whether the run is progressing or wedged, which is the request behind this phase.

Everything needed is already in hand and costs no tokens. `phx.runner.run_session` already receives every stream-json event through `on_event` (the heartbeat uses it), and those events carry the tool calls, the assistant's text and per-message token usage. The supervisor throws all of it away. This phase keeps the useful part, puts it in `state.json` and a periodic `progress` event in `run.jsonl`, and adds a `phx watch` command that redraws one line in place, so Nick gets a real feedback loop instead of polling.

## Decisions already made
- **ADR-0028**: the design decisions for this phase, taken at planning time. Follow them; if the build shows one is wrong, add the phase's own ADR that supersedes it rather than silently editing the prompt.
- **No LLM call anywhere in the progress loop.** The supervisor still never calls a model (ADR-0001). The progress content is derived only from stream events the runner already parsed.
- **`progress` is a new additive event and `state.progress` a new optional block.** An older `state.json` without it must still load (`RunState.from_json` already drops unknown keys and will simply leave the block absent).

## Goal
While a phase session runs, PHX records what the session is doing and how it is going, every few minutes, at zero token cost:

1. a `progress` event in `run.jsonl` at most every `progress_interval_s` (default 300 s, the "every five minutes" of Nick's request), plus one immediately when the *stage* of the work changes (claiming → working → testing → finishing) so a long edit block is not followed by five minutes of silence;
2. a `progress` block in `state.json` refreshed through the existing heartbeat, so `phx status` and `phx watch` can read it without parsing the log;
3. `phx status <repo>` shows the current activity, step counts, live tokens and cost, the age of the last stream event and an honest ETA;
4. `phx watch <repo>` follows a run live in one redrawn line, and prints the terminal events (pause, block, wait, finish) as normal lines;
5. a `warning` event and an amber line in `watch` when the session has been silent long enough to be suspicious, well before the idle timeout kills it.

## Tasks
1. **`src/phx/progress.py`** (new, stdlib only). A `ProgressTracker` that consumes stream events and holds the derived state:
   - `last_tool` (name + a **short, redacted description**: the file being edited/written/read, or the command being run, truncated to ~80 chars), `last_text` (the last assistant text or thinking line, ~120 chars, redacted, may be empty);
   - counters: `steps`, and per-tool counts (`edit`, `write`, `bash`, `read`, `grep`, `glob`, `other`); count a **completed** `tool_result`, not a `tool_use`, so a step means work actually finished — say which in the docstring and record the choice in the phase ADR;
   - `stage`: a coarse, honest label derived from the tool trail — `starting`, `working`, `testing` (a test/lint/type command is the most recent tool), `finishing` (a commit/merge/push is the most recent tool, or the session's last text mentions close-out), `unknown` when the trail gives nothing;
   - `tokens` / `cost_usd`: the running total from per-message usage, deduped by message id the way `Usage.from_messages` does, plus the session's `total_cost_usd` from the `result` event when it arrives;
   - `last_event_at` (monotonic and wall), `since_wall` (session start), `events`.
   Keep the parsing pure and fully unit-tested: feed it fixture events, never a real session. It must never raise on a malformed event.
2. **Wire it into the runner.** Add an optional `on_progress: Callable[[ProgressSnapshot], None]` to `run_session`, called at most every `progress_interval_s` and at once on a stage change (compare `stage`, and bucket `now - last_call` against the interval). Default `None` keeps every existing caller and test unchanged. `Usage` accounting for the final `SessionOutcome` must stay exactly as it is today — this is an addition, not a refactor of the accounting.
3. **Carry it in `state.json`.** Add a small serialisable dataclass (for example `Progress`) to `src/phx/state.py` with the fields `phx status` and `watch` need, an optional `progress: Progress | None` on `RunState`, and a `_build`-style decode in `from_json` the way `Pause` and `Wait` are handled. The supervisor's `_heartbeat` refreshes it from the tracker (reuse the existing 30 s throttle; do not add a second save path). Clear it when a session ends and set it while a usage-limit wait is pending, so `status` can say "waiting for capacity, wakes at …" instead of a stale activity line.
4. **The `progress` event.** In `log.event("progress", phase=…, reason=<one human line>, **fields)`, log the one-line reason plus the structured fields (stage, last tool, counts, tokens, cost, last-event age, elapsed, eta range). The `reason` must read well in `phx log` without any other context, for example:
   `phase 12d attempt 1, 47m elapsed · editing src/phx/supervisor.py · 38 steps (18 edit, 9 bash, 6 read) · 1.21M tokens, $1.83 · ~25m of ~80m typical left (median of 9 phases)`.
5. **The stall warning.** When the last stream event is older than a threshold (suggest half of `idle_timeout_s`, i.e. 15 min at the default), log a `warning` event **once per quiet spell** (`stalled_for_s`, the idle timeout that will fire), and clear it as soon as an event arrives. The warning must never fire while a single long-running tool (a test command) is in flight without saying so: name the tool and its elapsed time in the message, as `running uv run pytest (6m) — no event for 14m` rather than a bare alarm. `phx watch` shows it in amber.
6. **An honest ETA.** An agent cannot know how long its phase will take, so never invent a single number. Compute a **range** from the wall times of the phases PHX already completed in this plan, taken from the Phase Log Timeline bullets (`started` → `finished`, the same source the timeline generator uses) and fall back to `state.phases`, and show it as `~25m of ~80m typical left (median of 9 phases)`. With no completed phase to compare against, print `no estimate yet (first phase in this plan)`. When the stage is `testing` or `finishing`, add a plain-language hint rather than a smaller number. Put the median/range function in `progress.py` with tests for the zero-sample, one-sample and odd/even-sample cases. A deliberately wide or missing estimate is correct behaviour; a confident wrong one is not.
7. **`phx status`.** Extend `status_report` with a `progress` key (so `--json` exposes it too) and print, under `Phase:`: the activity line, the step counts, live tokens and cost, `last event Ns ago`, the stage and the ETA line. When `state.progress` is absent (an older state file or a supervisor that is not mid-session), print nothing extra. Follow the existing indentation and label style.
8. **`phx watch <repo>`** (new subcommand, registered in `COMMANDS` with this phase's number). A single redrawn status line (`\r` + pad to width, never a raw cursor escape) covering: phase and attempt, elapsed, stage, last activity, steps, tokens, cost, last-event age, ETA. It reads `state.json` and the lock file with a short poll (about 5 s), and when the state changes to `paused`, `stopped`, `finished`, `failed` or `waiting` it prints a normal line and either keeps the last frame on screen (`paused`/`waiting`, with the reason and the `phx resume`/`phx answer` hint) or exits 0 (`finished`, `stopped`, `failed`). `Ctrl-C` exits cleanly with status 0. `--json` prints one JSON object per change instead, for scripting. Handle the "no state file yet", "supervisor gone but state says running" and "non-TTY output" cases without tracebacks. Put the pure formatting in a testable function (`cli.py` is in the no-shell, no-TTY test path — see the coverage note in the Phase 07 log entry).
9. **Config and docs.** Add `progress_interval_s` (new default 300) to `Config` and `.phx/config.toml` parsing with the existing typed validation; validate a sane minimum (a value of 0 or less must be rejected with a clear `ValueError`, not spin). Document it in the user guide's config table. Update every doc listed under "What exists": the event list in the user guide, the status section, README, architecture, the spec's R10 (a progress record is part of "every decision and its reason") as an amendment only if the spec's text actually constrains it — read it first, do not add an amendment for something R10 already allows.
10. **Tests.** Unit tests for `progress.py` (stage transitions, counting, redaction of a secret inside a tool command, ETA ranges, malformed events). Runner tests with the fake `claude` asserting that `on_progress` fires at the interval, fires again on a state change inside the interval, and never fires for a silent session beyond the expected cadence. Supervisor tests asserting `state.progress` is populated, refreshed and cleared, and that the stall `warning` fires once per quiet spell. CLI tests for `status_report` with and without progress, and for `watch`'s formatting function including the `--json` shape, the finished/paused paths and non-TTY output. Add `tool_use` and `tool_result` emission to `tests/fakes/fake_agent.py` (or a new fake scenario) so a progress assertion has real event shapes to read; keep every existing fake scenario's output unchanged. Never launch a real session.
11. **Close out.** ADR for anything this phase decided that ADR-0028 did not settle (for example the tool_result-vs-tool_use choice, the stall threshold, or a rejected `stage` heuristic and why). ADR-0028 must be marked with this phase in the index.
