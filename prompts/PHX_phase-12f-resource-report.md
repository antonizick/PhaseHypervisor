# PHX Phase 12f: `phx report`, resource trends and optimization recommendations

**Model:** Opus 5.5 (`/model claude-opus-5-5`) · **Depends on:** 12e · **Branch:** `phase-12f-resource-report` · **Worktree:** `../PhaseHypervisor-phase-12f` · **Gate:** review

PHX already records, for every session it launches, how long it ran, which model and provider served it, how many tokens of each kind it used and what that cost, plus every wait, retry, timeout and block. Nothing reads those records back. To learn where the hours and dollars went, or whether they are trending up, Nick has to grep `run.jsonl` by hand, and the README currently has to say that PHX "does not yet ship a trend report". This phase adds `phx report`: it reads the records PHX already keeps, across every project, and prints how time, models, tokens and cost were used per month, quarter or year, together with deterministic, evidence-backed recommendations for using fewer resources. It writes no new data and calls no model.

## Decisions already made (ADR-0032)
- **No LLM call.** Every recommendation comes from a fixed, tested rule over recorded numbers and cites them. The supervisor-never-calls-a-model rule (ADR-0001) holds for the reporter too.
- **Read-only and additive.** The reporter reads `~/.local/state/phx/<repo>/run.jsonl` (and, only if needed, `state.json`) and never writes there. It does **not** read `sessions/*.jsonl` transcripts: they are large and may hold anything a session saw. If a field you need is missing from `run.jsonl`, add it as an additive field to the event that already exists, document it, and say so in your ADR; do not invent a new log.
- **Honest about what is measured.** Tokens, cost and model use exist only for sessions that `phx` launched. Manual `/phase` sessions leave no token or cost record, so they are not in the report and the report says so in its header, never estimating them. `cost_usd` is the list-price equivalent PHX records (`costBasis: "list"`), not an invoice: label it so wherever cost appears. A missing cost is *unknown*, never `$0`.
- **Plain, inspectable output.** Stdlib only (ADR-0010). Terminal tables, a stable `--json` schema, Markdown, and SVG in the timeline's visual style.

## Goal
`phx report` answers, for one project or all of them over any period:
1. **How much did it use?** Elapsed and active session time, waiting time (usage-limit waits, gate pauses), tokens by kind (input, output, cache read, cache write) and cost, per period, per project, per phase and per model.
2. **What did it achieve for that?** Phases completed, first-attempt completions, retries, blocks, timeouts, and the efficiency ratios built from them: cost per completed phase, tokens per completed phase, active hours per phase, share of spend on sessions that did not complete the phase, cache-read share.
3. **Which way is it trending?** The same figures per month, quarter or year, with the change from the previous period.
4. **What should be changed?** A short list of recommendations, each with the rule that fired, the numbers behind it and a concrete action, or an explicit "nothing crossed a threshold" when none fires.

## Tasks
1. **Loader.** `src/phx/report/` (a package, or `report.py` if small): read every `run.jsonl` under the state root, tolerating a truncated last line and unknown events and fields; yield typed records. Drop `dry_run`. Give each project its repo name from the directory. Never raise on one bad file; report it as a warning in the output. Do not follow symlinks out of the state root.
2. **Model.** A pure aggregation layer over those records, keyed by project, phase, model, provider and period. Define precisely and document in the module docstring: *active time* (sum of `duration_s` of sessions), *waiting* (sum of `wait_start`→`wait_end` spans, else `PhaseTotals.wait_s`), a phase's *completion* (a `verify` with `outcome` complete, once per phase per run, deduplicated if a resume reports it twice), *first-attempt completion* (completed with exactly one session and no retry or timeout), and *non-completing spend* (cost and tokens of sessions whose class is not `complete`). Unknown cost stays `None` and is counted separately (`sessions_without_cost`); sums never treat it as zero.
3. **Periods.** `--by month|quarter|year` (default `month`), `--since`/`--until` (`YYYY-MM-DD`, or a period like `2026-Q4`, local time), buckets from the event's `epoch` in the local zone. Include empty periods between the first and last so a trend line has no hidden gaps. Each period shows the change from the previous one; with no previous period, or a previous value of zero, show `n/a`, never a percentage of zero.
4. **Recommendations.** A rules module: each rule is a small pure function over the model returning zero or more `Recommendation(id, severity, title, evidence, action)`. Thresholds and minimum sample sizes live in one table at the top of the module, each with a one-line reason. A rule needs its minimum sample or it stays silent and the report says "not enough data for <rule> (n sessions, needs m)". Start with these and add none that you cannot test:
   - **R1 cost concentration:** phases whose cost is far above the median for the same model.
   - **R2 non-completing spend:** the share of cost and time spent on sessions that did not complete the phase (retries, timeouts, blocks, limit stops), listing the worst phases.
   - **R3 model fit:** for a phase on the strongest model that completed first time at low cost and short time, say a balanced model *may* suffice for similar phases; for a phase on a balanced model that needed repeated retries or blocks, say the strongest *may* save money. Advisory wording only; cite the numbers and the plan's rationale.
   - **R4 cache efficiency:** a low cache-read share of input, which points to sessions re-reading or re-creating large contexts.
   - **R5 waiting:** time lost to usage-limit waits and gate pauses, with the weekday and hour pattern if the data supports one.
   - **R6 timeouts:** `idle_timeout_s` and `wall_timeout_s` against the real session-duration distribution (too tight when sessions are killed near the limit, needlessly loose when none comes close).
   - **R7 trend:** cost per completed phase or non-completing share rising for two consecutive periods.
   - **R8 provider mix:** only descriptive (cost and success by provider); no recommendation unless the sample supports one.
   Every recommendation prints its evidence, the rule id and the threshold that fired, so Nick can disagree with it.
5. **Command.** `phx report [<repo> ...] [--all] [--by month|quarter|year] [--since X] [--until Y] [--exclude <repo> ...] [--state-root PATH] [--json] [--markdown [PATH]] [--svg DIR] [--vault]`. No repo and no `--all` means all repos under the state root with `phx-pilot` excluded unless named. Register it in `COMMANDS` with phase `12f`. Terminal output: a header (scope, period, as-of time, the manual-sessions and list-price caveats), then totals, a per-period table with trend arrows, per-model and per-project tables (top N, `--top`), and the recommendations. Respect `NO_COLOR` and a non-TTY; no ANSI when piped.
6. **`--json`.** A stable, versioned schema (`"schema": 1`) with every number the tables show plus the recommendations and the thresholds used; document it in the user guide with one example.
7. **`--markdown` and `--vault`.** `--markdown` prints the report as Markdown, or writes it to PATH. `--vault` writes a timestamped note under the vault (`PHX_VAULT_ROOT` as `src/phx/vault.py` resolves it), default folder `04 Resources/PHX Reports/` in the same PARA style the rest of the vault uses, with `[[wikilinks]]` to each project note that exists. It overwrites nothing: the file name carries the timestamp (`YYYY-MM-DD HHMM`). Skip the vault silently with a clear message when no vault root is configured, as the run summary does.
8. **`--svg DIR`.** Write, in the timeline's visual style (inline CSS, light and dark, a `<title>` per mark, a readable plain-text fallback line under each chart), at least: cost per period (bars), cost per completed phase (line), active hours per period, and the model mix per period (stacked share of cost). Each chart states its scope and as-of time, labels list-price cost as such, and marks periods with no data rather than drawing zero. Deterministic output: the same input yields byte-identical SVG.
9. **Docs and README.** `docs/PHX_USER_GUIDE.md` gets a `phx report` section (what each number means, the definitions from task 2, the rules and thresholds, a **synthetic** example, how to read a recommendation, how to disagree with one). `README.md`: replace the sentence saying PHX has no trend report with what the command now does, add `phx report` to the command table, and keep every claim checkable. Add `phx report` to `docs/PHX_ARCHITECTURE.md`, the `/phx` command if the plugin lists commands (mirror in `docs/PHX_GETTING_STARTED.md` and Nick's playbook only if anything under `plugins/` changes), and `CHANGELOG.md`. Any example output in public files uses synthetic data, never Nick's real figures or private repo names (ADR-0023, ADR-0031).
10. **Real-data check (read-only).** Run `phx report --all` against the reference machine's real state root, read the output as Nick would, and sanity-check three numbers by hand against `run.jsonl` (a total cost, a phase count, one model's share). Record in the Phase Log only aggregate figures and the checks you made, not private repo names or per-project tables. Show Nick the Markdown and the charts (paths in the scratchpad) in your final message, since this is a `review` phase.

## Out of scope
- Any LLM call, narration or summarisation (ADR-0032). Estimating cost or tokens for manual `/phase` sessions. Reading session transcripts. Budget enforcement or automatic changes to `.phx/config.toml` or to the plan's model column: the report advises, Nick decides.
- Changing how `phx run` launches, verifies or logs sessions, beyond an additive field if task 1 proves one is missing.
- Pricing tables or currency conversion; the report uses the cost PHX recorded.
- A web dashboard, a daemon, a database, or scheduled reports (a cron job calling `phx report --vault` is a follow-up Nick can set up himself).
- A version bump, tag or GitHub Release (ADR-0026 still applies).

## Tests
- Fixtures: small **synthetic** `run.jsonl` sets under `tests/fixtures/report/` (no real project names, phase titles or paths; the deny-list test must cover the directory): a clean multi-period history, a retry-heavy phase, null costs, a truncated last line, a `dry_run` mixed in, a resumed phase reported twice, two projects, an empty month in the middle, and sessions across a quarter boundary and a year boundary.
- Aggregation: totals equal the sum of their parts at every grouping; unknown cost is excluded from sums and counted; dry runs and duplicates do not count; period buckets use the local zone and include empty periods; trend `n/a` after a zero.
- Each rule has a case where it fires with the expected evidence, a case where it stays silent, and an insufficient-data case; thresholds are read from the one table.
- CLI: `phx report` on the fixtures in every output mode (`--json` validates against the documented schema; Markdown and tables contain the caveats; `--svg` output is byte-identical on a second run and valid XML; non-TTY output has no ANSI), an empty state root (clear message, exit 0), an unreadable file (warning, others still reported), `--exclude`, `--since` after `--until` (clear error). `COMMANDS` contains `report` with phase `12f`.
- The reporter never writes under the state root: a test makes the fixture directory read-only and runs it. No network, no real Claude, no `ai-provider`.
- `uv run pytest`, `uv run ruff check .`, `uv run ruff format --check .`, `uv run mypy src` and pre-commit stay clean; coverage of the new module at least the project's level.
