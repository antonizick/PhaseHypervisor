# Security Policy

## Scope
PhaseHypervisor is a **local tool** that starts AI agent sessions (Claude Code) with **bypassed permissions** on its owner's machine, inside repositories under the owner's control. It is not a service, opens no network listener and has no multi-user mode. Security reports are in scope when they show that PHX could be made to act outside that boundary: leaking secrets, running content from a repo or agent output as commands, or acting on the wrong repository.

## Reporting a vulnerability
Please do not open a public issue. Email nick@antonizick.com with a description, reproduction steps and the PHX version or commit. If the repository is hosted on GitHub, you may use its private vulnerability reporting instead. Expect an acknowledgement within a few days; this is a personal project, so there is no formal SLA.

## Security baseline (spec §4.3, S1–S5)
The full threat model, with each threat's rating, its mitigation, the test that covers it and any accepted residual risk, is [`docs/PHX_THREAT_MODEL.md`](docs/PHX_THREAT_MODEL.md) (Phase 11).

- **S1, bypass permissions are local-only.** PHX runs only on the owner's machine, in repos under the work root, and refuses to run as root. `phx run`/`resume` enforce both (Phase 07): the repo's main checkout must be under `$PHX_WORK_ROOT`, default `~/Work` (set it to your own projects folder), and the effective UID must not be 0. Phase sessions are confined to their repo and worktree by the `/phase` rules, and a risk-stop rule makes an agent stop and ask (or block the phase with the question recorded) when an action looks high-risk or irreversible.
- **S2, no secret leakage.** Everything written to logs passes through a redaction step, and PHX never reads or copies `~/.config/ai-provider/openrouter.key` itself. Session transcripts (`sessions/<phase>-<n>.jsonl`) and stderr tails are redacted line by line before they are written. Redaction covers the token shapes `sk-or-`, `sk-ant-`, `gh*_` and `github_pat_`, bearer headers, and assignments to any upper-case `*TOKEN`, `*API_KEY`, `*SECRET` or `*PASSWORD` name in shell, YAML, JSON and escaped-JSON form, keeping JSON valid (Phase 11). `tests/redaction_audit.py` checks state directories for anything left over; the Phase 10 pilot state audited clean. To log which OpenRouter model serves a phase, the runner (Phase 05) runs `ai-provider env`, whose output contains the key: PHX keeps only an allowlist of non-secret variables (base URL, model mappings, token caps), redacts those too, and drops the rest unread, so the key is never logged, stored or passed on by PHX. Phase sessions get `ai-provider`'s environment from `ai-provider` itself, not from PHX. The preflight session (Phase 08) is told to check that key and credential files exist and variables are set without reading or printing them, and its assembled prompt is saved with mode 0600.
- **S3, untrusted content.** Repo content, plan text and agent output are treated as data. PHX parses them with strict patterns and never evaluates them or passes them unquoted to a shell. The plan parser (Phase 04) only reads `main` through `git` with argument lists, matches text with regular expressions, and never runs a command found in a plan (the test command is only extracted). Verification (Phase 06, ADR-0015) runs the plan's test command only in a temporary clone of `main`, never through a shell: a small interpreter accepts `&&`, `cd`, `NAME=value`, quotes and globs confined to the clone, and refuses pipes, redirects, variables and command substitution. The test environment drops `PHX_AUTO` and API keys. The triage session that reads a stopped phase's messages has no tools (`--tools ""`, one turn, outside the repo), and its prompt marks that text as data, so text planted in a repo can at most change the wording of a summary. The preflight prompt (Phase 08) quotes short sentences from the remaining phase prompts and question cells (lead text, clipped to 240 characters, between « » and marked as data); that session is interactive, with the owner present and the owner's normal permission settings (not bypassed), and it may only change the plan, the decisions file, `.phx/preflight.json` and the Obsidian note. The only write PHX makes to a repo on its own is the `⛔ Blocked` status commit, under the claim protocol's preconditions. Repo text cannot redirect PHX's writes: the Obsidian note named in `CLAUDE.md` must resolve inside `$PHX_VAULT_ROOT` (default `~/Documents`), and `phx preflight --record` refuses a symlinked `.phx/` or `preflight.json` (Phase 11). Text quoted into the triage and preflight prompts cannot close its data block. A timed-out test command is killed with its whole process group.
- **S4, one writer.** A machine-wide lock plus a per-repo lock prevent two supervisors, or two phases of one repo, from running at once. Both are `flock` locks under `$XDG_RUNTIME_DIR/phx/` (directory mode 0700) held for the supervisor's whole life; a manual `/phase` sees the per-repo lock and stops (contract §8), and stops too if that check cannot run (fail-closed, ADR-0020). `phx answer` refuses while a supervisor holds the lock and, like the `⛔` repair, only commits the plan file when the main checkout is on `main` with that file clean. `state.json` is written atomically with mode 0600. `phx preflight` refuses while a supervisor holds the lock or a phase is `🔄`, and `phx preflight --record` commits only `.phx/preflight.json`, from a main checkout on `main` whose plan file is clean.
- **Detached runs** (`phx run --detach`, Phase 07) get only an allowlist of environment variables (paths, locale, display and session-bus addresses, `PHX_WORK_ROOT`, `PHX_VAULT_ROOT`); API keys or tokens in the launching shell never reach the systemd unit. Notifications carry phase IDs, reasons and the triage summary (already redacted), never secrets.
- **S5, irreversible actions stay human.** Making a repository public, publishing a release and force-pushing shared history always stop for the owner. A preflight never pre-approves them (ADR-0017): it records the details and a `review` Gate, and the phase still asks at that moment.

Secrets and personal data are never committed; `.gitignore` and (from Phase 02) a pre-commit secret scan enforce this.

## What installing the plugin lets agents do (Phase 12a)
The `phased-project` plugin (`plugins/phased-project/`) contains only instructions: one skill and one command. It has no hooks, no MCP servers and no executables, and it asks for no settings. Installing it lets Claude, when you invoke it (or when you ask for a phased plan), write a project's spec, plan, prompts, `CLAUDE.md` and `.claude/commands/` files, run `git` (init, commit, and with the generated git authority rule, merge and push), optionally create a **private** GitHub repo with `gh`, and with `/phx` run the `phx` CLI. All of that goes through Claude Code's normal tools and your session's permission mode.

The caveat is **hands-off runs**: `phx run` starts every phase session with `--permission-mode bypassPermissions`, so a phase agent can run any command as your user without asking. The generated rules (risk rule, scope, Gates, block-with-question) are instructions to the model, not a sandbox; text planted in a repo could try to steer the agent (threat model T1, T2). Run `phx` only on repos you trust, on a machine where your user's reach is acceptable, never as root, and read the [threat model](docs/PHX_THREAT_MODEL.md). Manual `/phase` sessions never bypass permissions unless you set that yourself.

## Supported versions
Only the latest release and the latest commit on `main` are supported.
